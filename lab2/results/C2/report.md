## Подходы к хранению состояния LLM-агентов

В изученных источниках выделяются три основных подхода.

**1. Долговременная память (memory).** Память о пользователе хранят как документы с пространствами имён, например по пользователю [ev_ebdefa950818]. Обновление памяти идёт явными операциями записи, а не неявно из каждого сообщения [ev_8bf586bd7f75].

**2. Чекпоинты графа (checkpointer).** Checkpointer сохраняет состояние графа после каждого шага (super-step), поэтому выполнение можно продолжить с последней сохранённой точки [ev_8bb76e41ec6f]. Чекпоинт содержит значения каналов состояния, версию и список ожидающих записей узлов [ev_e005d16ce094]; идентификатор потока thread_id связывает последовательность чекпоинтов одного диалога или задачи (checkpoint-3).

**3. Durable execution.** Durable execution сохраняет прогресс workflow так, что после сбоя выполнение продолжается с того же места [ev_1aec2c67eeee]; недетерминированные действия, включая вызовы LLM, выносят в activities с повторами, а таймауты разделяют на время ожидания запуска и время выполнения (durable-2).

**Бэкенды.** Для облачных развёртываний состояние хранят в управляемой базе с резервным копированием; Redis даёт низкую задержку, но требует настройки персистентности [ev_6e2c52595560]; PostgreSQL используют, когда несколько рабочих процессов обращаются к одному хранилищу (backends-3).

## Ограничения подходов

- **Память:** векторная память не гарантирует точного совпадения фактов [ev_72782ad35d5b]; память накапливает ошибочные факты, если их не проверять [ev_6d81180a8113].
- **Чекпоинты:** хранение полной истории чекпоинтов быстро увеличивает объём базы [ev_c034215ec9f4]. Спорное утверждение «чекпоинт гарантирует однократное выполнение каждого инструмента» опровергается: если процесс упал после вызова инструмента, но до записи чекпоинта, шаг выполнится повторно; нужны ключи идемпотентности [ev_2d1569d7cfeb].
- **Durable execution:** не делает внешние эффекты идемпотентными автоматически [ev_f0581dab5ae7].
- **Бэкенды:** сетевое хранилище добавляет задержку к каждому шагу агента [ev_618d605ab57d]; без AOF или снимков Redis теряет данные — для долгих задач надёжность важнее задержки (backends-3).

## Сравнение подходов по ограничениям

| Подход | Что хранит | Ключевые ограничения |
|---|---|---|
| Память (memory) | Факты о пользователе/мире, документы с пространствами имён | Нет гарантии точного совпадения фактов [ev_72782ad35d5b]; накопление ошибочных фактов [ev_6d81180a8113] |
| Чекпоинты | Состояние графа после каждого super-step: каналы, версия, ожидающие узлы [ev_e005d16ce094] | Рост объёма базы при полной истории [ev_c034215ec9f4]; повторное выполнение шага при сбое между вызовом и записью [ev_2d1569d7cfeb] |
| Durable execution | Прогресс workflow, activities с повторами | Внешние эффекты не идемпотентны автоматически [ev_f0581dab5ae7] |
| Бэкенды (Redis/PostgreSQL) | Состояние в управляемой/сетевой БД | Задержка сети на каждом шаге [ev_618d605ab57d]; Redis без AOF/RDB теряет данные [ev_6e2c52595560] |

Вывод: подходы дополняют друг друга — память отвечает за долговременные факты, чекпоинты и durable execution — за восстановление выполнения, а выбор бэкенда балансирует задержку и надёжность. Ни один подход сам по себе не решает проблему идемпотентности внешних эффектов.
