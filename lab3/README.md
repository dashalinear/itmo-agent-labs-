# Лабораторная 3. Гибридный навигационный поиск L0/L1/L2

В этой лабе я развила организатор из лабы 1 и harness из лабы 2 в систему из четырёх агентов:
- **агент-загрузчик** раскладывает корпус по папкам и строит уровни L0/L1/L2 в Elasticsearch;
- **основной агент** отвечает на вопросы;
- **deep search** — субагент для многораундового исследования;
- **exhaustive search** — субагент, который полностью обходит конечную область без top-k.

Все четыре агента сделаны на библиотечном ReAct-агенте `langchain.agents.create_agent` (LangGraph) с middleware harness из лабы 2. Структуру уровней, загрузку и навигацию я написала сама, OpenViking и похожие готовые решения не использовала. Тексты, метаданные и векторы хранятся в Elasticsearch.

## 4. Уровни L0/L1/L2

| Уровень | Где | Содержимое | Навигация |
|---|---|---|---|
| **L0** — весь корпус | `.harness/corpus/l0.json` | папки и все документы: `document_id`, путь, заголовок, описание, hash, наличие L1, число фрагментов L2 | `corpus_overview(cursor)` (постранично по 25), `list_documents(folder, cursor)` → `get_l1` |
| **L1** — документ | `.harness/corpus/l1/<id>.json` + ES `itmo_lab3_l1` | название, описание, **summary, написанные агентом**; разделы с `section_id`, диапазонами строк и summary; hash версии | `get_l1(document_id)` → разделы с числом фрагментов и первым `fragment_id` → `read_section` |
| **L2** — исходные тексты | `.harness/corpus/l2/<id>.json` + ES `itmo_lab3_l2` | **все** фрагменты: `fragment_id`, `document_id`, `section_id`, строки, страницы, `prev_id` / `next_id`, hash; текст всегда вырезается из файла по диапазону | `read_section` (постранично), `read_fragment`, `neighbor_fragment`, `open_source(document_id, строки)`, возврат `get_l1` |

Решения по содержимому принимает агент. Он выбирает папку (как организатор в лабе 1), пишет название, описание и summary и задаёт разделы диапазонами строк. Документ без заголовков он размечает сам. Код (`write_l1`) только проверяет разделы: они должны идти по порядку, не пересекаться, лежать внутри файла и покрывать каждую непустую строку.

Фрагменты L2 нарезаются детерминированно внутри разделов агента: не больше 10 строк или 800 символов, граница проходит по пустой строке. Идентификатор `fragment_id = uuid5(document_id | content_hash | start | end)` не меняется, пока не меняется документ, поэтому повторная индексация неизменённого документа ничего нового не создаёт.

`validate_corpus` работает без модели. Он сверяет L1 с версией файла, покрытие разделов, `fragment_id` с ключом, принадлежность фрагмента разделу, непустой текст на этих строках, цепочку prev/next, отсутствие пересечений и число фрагментов в ES с реестром.

В Elasticsearch два индекса с `dynamic: strict`, анализатором `russian` с подполем `standard` и keyword-полями для фильтров.

| Индекс | Поля | Embedding |
|---|---|---|
| `itmo_lab3_l1` | `title`, `description`, `summary`, `structure` (заголовки и summary разделов), `folder`, `path`, `content_hash` | `embedding` (`dense_vector` 384, cosine) от title + description + summary + structure |
| `itmo_lab3_l2` | `text`, `section_title`, `doc_title`, строки, страницы, `ordinal`, `prev_id`/`next_id`, `folder`, `path` | `embedding` от «заголовок раздела + текст» |

Для embeddings я взяла `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` через `fastembed` 0.9.1 (ONNX Runtime, CPU, без torch). Векторы размерности 384, нормированные, считаются локально. Перефраз «с какой периодичностью копируют журнал событий на запасной диск» в контрольной проверке (`results/search_probe.json`, Q6) находит нужный документ `st_snapshot_policy.md` на втором месте. Первым идёт фрагмент о событийной модели из `st_event_sourcing.md` (косинус 0,823): он близок по словам «журнал событий», но о копировании не говорит. Слабое место у модели тоже есть: короткий разговорный вопрос «как часто делают бэкап лога событий» находит этот абзац только на 22-м месте. Поэтому на перефразах агенту лучше переформулировать запрос или сочетать вектор с grep/full-text.

## 5. Поисковые tools и наборы агентов

| Вид | L1 | L2 |
|---|---|---|
| Полнотекстовый `search_fulltext(query, level, folder?, document_id?, size, cursor)` | BM25 по title, description, summary, structure | BM25 по `text` и `section_title`; подсветка |
| grep `search_grep(pattern, level, regex?, …, cursor)` | буквально или regex по полям записей L1: документ, поле, `section_id`, смещение | буквально или regex по строкам исходного файла: документ, **точная строка**, страница, `fragment_id`; порядок корпуса, без ранжирования, курсор до последнего совпадения |
| Векторный `search_vector(query, level, …, k≤10)` | kNN по embedding L1 | kNN по embedding фрагментов |

В каждом результате есть идентификаторы и подсказка, как перейти на следующий уровень (`next`). Если результат не помещается в лимит вывода, он уходит в артефакт harness, и агент читает его через `read_artifact` / `search_artifact`.

| Агент | Tools |
|---|---|
| загрузчик | файловые tools лабы 1, каталог, skills, MCP ES лабы 1, `doc_info/read_pages/read_lines/search_text`, `doc_outline`, `write_l1`, `index_document`, `corpus_status`, `validate_corpus`, `update_plan/task_progress/complete_task/stop_partial`, артефакты |
| основной | навигация L0/L1/L2, три вида поиска на L1/L2, `cite_fragment`, `start_subagent`, `subagent_status`, `subagent_result`, артефакты |
| deep | та же навигация и поиск, `cite_fragment`, `update_plan`, `submit_result`, `stop_partial` |
| **exhaustive** | `area_define`, `area_next`, `area_grep`, `area_fulltext`, `record_mention`, `area_coverage`, `get_l1`, `corpus_overview`, `list_documents`, `submit_result`, `stop_partial`. **Нет** векторного, ранжированного поиска и top-k |

Skills: `build_corpus_levels` (загрузка), `navigate_corpus` (ответы), `exhaustive_scan` (полный обход), плюс skills лаб 1–2.

## 6. Делегирование субагентам

Основной агент передаёт субагенту естественно-языковой `request`, это и есть содержание задачи. Технические метаданные идут отдельно: `scope_folder` задаёт агент, а `parent_task_id`, `corpus_id` и бюджет `DEFAULT_SUB_LIMITS` ставит код. Субагент — отдельная задача в `state.db` (`spec.parent_task_id`) со своими `thread_id`, checkpoints, системным промптом, контекстом и tools.

Выход `subagent_result`:
- `status`, `findings`, `open_questions`;
- `evidence` — список `{evidence_id, document_id, fragment_id, path, lines, quote, claim}`;
- `usage` — токены, вызовы модели и tools, компактификации;
- для exhaustive дополнительно `coverage` — прочитано / всего по документам и непрочитанные диапазоны.

Вызов неблокирующий. `start_subagent` создаёт подзадачу, запускает её как `asyncio`-задачу в процессе CLI и сразу возвращает `task_id`. Пока субагент работает, основной агент отвечает на следующие реплики: диалог ждёт ввод через `asyncio.to_thread`, и цикл событий не блокируется. Состояние агент смотрит через `subagent_status`, результат забирает через `subagent_result` (с коротким ожиданием до 20 с, чтобы основной агент не зависал). Подзадачу можно продолжить и в новом процессе: `resume --task-id M1-exhaustive1`. DeepAgents я не использовала, реализация своя, на `create_agent` и TaskRunner лабы 2. Если субагент закончил ход без `submit_result`, менеджер субагентов один раз дописывает ему сообщение с просьбой сдать итог (подробно в разделе 9).

Бюджет общий. `ChainedBudget` перед каждым вызовом LLM субагента проверяет и его собственный лимит, и остаток родителя. Токены субагента записываются в обе задачи, так что они входят в общий лимит токенов. Вызовы модели и tools субагента родителю не добавляются: у основного агента есть лимит вызовов на один ход диалога, и фоновые субагенты съедали бы его. Их вызовы ограничены собственными лимитами субагента.

Deep search разбивает задачу на подвопросы (`update_plan`), делает несколько раундов поиска на L1/L2 с переходами между уровнями, цитирует (`cite_fragment`) и возвращает открытые вопросы. `submit_result` принимается, только если было не меньше 2 поисковых вызовов и 2 evidence, хотя бы один поиск шёл по L2, в findings есть ссылки хотя бы на min(3, число evidence) настоящих `evidence_id` и список открытых вопросов не пустой. Если findings пустые, итог собирается из evidence с их id.

Exhaustive search работает без top-k:
- `area_define` фиксирует по L0 конечную область: все документы и все их фрагменты.
- `area_next(cursor, no_mention)` выдаёт фрагменты в порядке корпуса (путь, порядковый номер) с полным текстом.
- Порция считается прочитанной, только когда агент запрашивает следующую по `next_cursor`. При этом для каждого фрагмента прошлой порции нужен вердикт: записанное упоминание или его id в `no_mention`. Иначе приходит ошибка `verdict_required` со списком фрагментов без вердикта, а вердикты пишутся в событие `no_mention_verdicts`. Если перед остановкой по бюджету или сбоем порция была выдана, но не подтверждена, после resume по `resume_cursor` она выдаётся снова. Так ни одна часть не теряется.
- `area_grep` (строки) и `area_fulltext` (ES-запрос как фильтр, сортировка по пути, `search_after`, без score) читаются постранично до `done=true`.
- `submit_result` проходит, только если прочитаны **все** фрагменты области. Summary L1 не даёт права пропустить L2. К findings код дописывает число упоминаний по каждому документу, посчитанное по evidence, а не по тексту модели. `evidence_id`, которых нет в задаче, `submit_result` обоих субагентов отклоняет (`unknown_evidence`).
- Когда кончается бюджет, вызывается `stop_partial`. В реестре (`state.db`, `unit=fragment`) остаются число и список обработанных и оставшихся документов и диапазонов, а `resume` продолжает с `resume_cursor`.

**Первый прогон диалога (M1) и что в нём сломалось.** Ходы 1–9 прошли так же, как в M2. На ходе 10 нашлись две ошибки в harness:
1. Проверка цитат вырезала «N: » внутри текста («Шаг 2: …»), и цитата переставала совпадать с источником.
2. Не было защиты от зацикливания. Модель около 150 раз повторила один и тот же grep и израсходовала весь бюджет задачи (200 вызовов), так что ходы с субагентами не выполнились.

Что я исправила после M1:
- номер строки вырезается только в начале строки цитаты;
- **no-progress guard**: одинаковый вызов с тем же результатом на третий раз получает ошибку с подсказкой, на шестой ход останавливается;
- лимит 30 вызовов модели на один ход диалога (субагенты его не наследуют);
- `submit_result` без аргументов собирает итог из evidence. До этого EXP1 после полного покрытия 30 раз вызывал `submit_result({})` и остался `paused`.

На каждое исправление есть тест.

**Прогон делегирования M3 и второй сбой.** Сценарий был тот же, что в M4.
1. `M3-deep1` 38 раз вызвал `read_section` и ни разу `cite_fragment`: после компактификации он перечитывал уже прочитанные разделы. В итоге 0 evidence.
2. На ходе 5 основной агент не передал полный обход субагенту, а начал grep по `storage` сам. Ответ grep не поместился в лимит и ушёл в артефакт, модель не увидела `next_cursor` и шесть раз подставила выдуманный курсор. No-progress guard остановил ход, и exhaustive в M3 так и не запустился.

Что я исправила после M3 (коммит `108bc4d`):
- страница grep теперь всегда помещается в лимит одного ответа, и `next_cursor` видно; курсор, которого инструмент не выдавал, отклоняется с понятной ошибкой;
- harness помечает повторное чтение уже прочитанного раздела и после 5 чтений без цитат напоминает процитировать; в промпте deep требуется цитировать сразу после чтения;
- в промпт основного агента я добавила правило: просьбу просмотреть все документы области он всегда передаёт exhaustive-субагенту; в демо-диалоге реплика теперь прямо называет полный обход.

M4 — тот же диалог после исправлений: deep собрал 17 evidence вместо 0, exhaustive запустился из диалога и завершился.

**Что ещё было не так в прогонах M2–M4.** Это я нашла, когда проверяла результаты, и исправила.
- **Deep ни разу не вернул итог.** M2-deep1 остановил лимит 30 вызовов на ход, M4-deep1 — бюджет 40 вызовов, и до `submit_result` не дошёл ни один. Теперь:
  - лимит deep — 60 вызовов;
  - когда остаётся не больше 6 вызовов, каждый результат инструмента несёт `harness_budget` с требованием сдать итог;
  - если бюджет всё же кончился, `subagent_result` отдаёт итог, собранный кодом: `result: "partial"`, выводы по цитатам с `evidence_id`, открытые вопросы из незавершённых шагов плана и причины остановки. Пустого результата больше не бывает, и частичный не выдаётся за полный.
- **Выдумки основного агента в M2.**
  - На ходе 12 агент без вызова инструментов назвал несуществующие документы `data/ops/ops_runbook.md` и другие.
  - На ходе 13 ложно сообщил, что субагент завершён.
  - На ходе 15 вернул нечитаемый ответ «。…».

  Теперь после каждого ответа харнесс кодом проверяет, есть ли названные пути `data/...` в L0 и не пустой ли ответ. Ответ с ошибкой один раз возвращается агенту на исправление, в трассе это ход `chat-recheck`. В промпт я добавила правило: о статусе субагента можно говорить только после `subagent_status` в этом же ходе. В M4 на те же вопросы агент ответил верно.
- **Запрос к deep в M2 уже содержал ответ** («РС-7, PostgreSQL 16, Ирина Ковалёва…»), потому что вопрос про РС-7 был задан раньше. В новом диалоге `demo/dialog_final_ru.txt` deep запускается до этого вопроса, а пользователь не называет инструменты.
- **Загрузка.**
  - Пауза ING1 пришлась на начало, когда переносов ещё не было.
  - «Повтор без дублей» (ING3) я проверила только на пустой папке.
  - MCP лабы 1 загрузчик не вызывал.

  Теперь CLI до запуска агента убирает файлы с уже известным содержимым в `rejected/` (событие `duplicates_skipped`), а промпт загрузчика требует сохранить основную выдержку каждого нового документа через MCP (`upsert_excerpts`, проверка `search_excerpts`).
- **Манифест корпуса.** `corpus/manifest_frozen.json` (`document_id`, путь, заголовок, hash) выгружается командой `export`.
- **Контрольные упоминания.** Все 36 помечены кодом `[L-ST-xx]`, поэтому `area_grep "L-ST-"` находит их без смыслового чтения. Так сделали M2-exhaustive1 и EXP1. ## 11. Ограничения

- Обновление и удаление документов и версионирование я не делала. При изменённом hash `index_document` перестраивает L2 документа и удаляет устаревшие фрагменты, но отдельного сценария замены нет.
- Неблокирующие субагенты живут в процессе CLI: при выходе из `chat` CLI ждёт их завершения. После аварийного выхода подзадачу можно продолжить командой `resume`.
- Deep-субагент может израсходовать свой лимит вызовов до `submit_result`, как M4-deep1. Evidence и частичный отчёт при этом сохраняются, а `resume --task-id M4-deep1 --set max_model_calls=60` продолжает его с того же места. После исправлений, если бюджет всё же кончился, `subagent_result` отдаёт итог, который harness собрал из evidence и плана (`result: partial`, `compose_partial`).
- grep L2 при каждом вызове читает исходные файлы из L0. Для корпуса из десятков документов это быстро, а для миллионов фрагментов понадобился бы grep по ES-полям.

## 12. Выводы

Уровни L0/L1/L2, три вида поиска на двух уровнях и переходы между уровнями работают: `validate_corpus` не находит проблем на 332 фрагментах, а `probe` находит Q1–Q6. Загрузчик пережил и отказы сервера (ING1), и убитый процесс (ING4), а повтор тех же файлов не создал дублей (ING5). Больше всего времени у меня ушло на субагентов: deep долго не мог сдать итог, и это пришлось чинить несколько раз (бюджет, итог из evidence, резерв 6144 токенов, одно дополнительное сообщение). В финальном прогоне M9 deep и exhaustive оба завершились через `submit_result` параллельно, deep за один запуск, пока основной агент отвечал на другие вопросы с цитатами L2. Ни один ответ основного агента не пришлось возвращать на исправление. На перефразе агент выбрал full-text по L1, а не векторный поиск, и всё равно нашёл нужную строку. Exhaustive во всех прогонах читает все 47 фрагментов `storage`. С вердиктом по каждому фрагменту M9-exhaustive1 и EXP5 ни разу не получили `verdict_required`, но L-ST-30 они всё равно пропустили. Эта строка — скорее автоматическая проверка, чем ограничение, и стоит во фрагменте, где другие ограничения записаны, так что правило по фрагменту её не ловит. Слабые места остаются и у deep: в M9 после 10 компактификаций его итоговый текст отстал от собранных evidence, а `fragment_id` в нём сокращены. Основной агент это частично исправил, потому что строил ответ по evidence. Partial и resume обхода работают без потерь и повторов (EXP3, EXP5).
